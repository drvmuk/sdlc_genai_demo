# 1. Conceptual Data Model

- Entities:
  - Customer
    - Represents individual customers loaded from a source CSV
  - Order
    - Represents individual orders loaded from a source CSV
  - OrderSummary
    - Represents historical and current joined records of Customer and Order with SCD Type 2 logic
  - CustomerAggregateSpend
    - Represents daily aggregate spend per customer

- Relationships:
  - Customer 1 -- * Order (via CustId)
  - Customer * -- * OrderSummary (via CustId, SCD Type 2 history maintained)
  - Order * -- * OrderSummary (via CustId)
  - OrderSummary * -- * CustomerAggregateSpend (via Name, Date)

- Business Definitions:
  - Customer: Entity containing customer profile data (CustId, Name, EmailId, Region)
  - Order: Entity containing purchase records (OrderId, ItemName, PricePerUnit, Qty, Date, CustId)
  - OrderSummary: Entity representing SCD Type 2 historical join of Customer and Order (including all fields from both)
  - CustomerAggregateSpend: Entity representing aggregated spend per Name/Date

# 2. Logical Data Model

- Entities and Attributes:
  - Customer
    - CustId (Primary Key)
    - Name
    - EmailId
    - Region

  - Order
    - OrderId (Primary Key)
    - ItemName
    - PricePerUnit
    - Qty
    - Date
    - CustId (Foreign Key to Customer)

  - OrderSummary
    - CustId
    - Name
    - EmailId
    - Region
    - OrderId
    - ItemName
    - PricePerUnit
    - Qty
    - Date
    - [SCD Type 2 fields: StartDate, EndDate, Active] (per business rules, not explicitly defined)

  - CustomerAggregateSpend
    - Name
    - TotalAmount
    - Date

- Relationship and Cardinality Rules:
  - Customer to Order: 1-to-many (1 customer can have multiple orders)
  - Order and Customer to OrderSummary: Many-to-many (history-tracked relationship), joined on CustId
  - OrderSummary to CustomerAggregateSpend: Many-to-many, grouped by Name/Date

- Keys:
  - Each entity's primary keys as described
  - Foreign key: Order.CustId references Customer.CustId

- Normalization Notes:
  - Entities normalized to 3NF
    - No repeating groups
    - Non-key attributes depend only on primary key
    - No transitive dependencies

- Business Rules per Entity:
  - Order: TotalAmount = PricePerUnit × Qty (derived, stored in downstream tables)
  - Customer/Order: Remove records with "Null"/Null literals, remove duplicate records
  - OrderSummary: Apply SCD Type 2 change handling—maintain historical records with status indication

# 3. Physical Data Model

- Table: customer
  - CustId           | VARCHAR   | PK
  - Name             | VARCHAR
  - EmailId          | VARCHAR
  - Region           | VARCHAR

- Table: order
  - OrderId          | VARCHAR   | PK
  - ItemName         | VARCHAR
  - PricePerUnit     | DECIMAL
  - Qty              | INTEGER
  - Date             | DATE
  - CustId           | VARCHAR   | FK to customer.CustId

- Table: ordersummary
  - CustId           | VARCHAR
  - Name             | VARCHAR
  - EmailId          | VARCHAR
  - Region           | VARCHAR
  - OrderId          | VARCHAR
  - ItemName         | VARCHAR
  - PricePerUnit     | DECIMAL
  - Qty              | INTEGER
  - Date             | DATE
  - StartDate        | DATE      | SCD2 tracking (if implemented)
  - EndDate          | DATE      | SCD2 tracking (if implemented)
  - Active           | BOOLEAN   | SCD2 tracking (if implemented)

- Table: customeraggregatespend
  - Name             | VARCHAR
  - TotalAmount      | DECIMAL
  - Date             | DATE

- Indexing Strategy:
  - customer: PK on CustId
  - order: PK on OrderId, index on CustId
  - ordersummary: indexes on CustId, OrderId; if SCD2, composite index on (CustId, StartDate)
  - customeraggregatespend: index on Name, Date

- Partitioning, Clustering, Storage:
  - ordersummary, customeraggregatespend partitioned by Date if volume is high
  - Tables stored as Delta tables (per requirements)
  - No explicit clustering or Z-ordering defined in requirements

- Constraints:
  - PK and FK as noted
  - Unique constraint on customer.CustId, order.OrderId
  - Referential integrity between order.CustId and customer.CustId

- Performance Optimization:
  - Remove null or duplicate records before load
  - Precompute aggregates for customeraggregatespend to optimize query performance

# 4. Naming Conventions

- All table and column names in lower_case, snake_case as per provided requirements
- Primary keys: <entity>_id where possible (e.g., cust_id, order_id)
- Foreign keys use identical names to referenced keys
- Computed columns have descriptive names (e.g., TotalAmount)

# 7. Technology-Agnostic Statement

Constraints, normalization, and physical optimizations are specified but can be adapted to the target system’s capabilities. No implementation-specific syntax or reserved words are used.
