# 1. Conceptual Data Model

- Entities:
  - Customer  
    - Represents individual or business customers providing orders.
  - Order  
    - Represents purchase transactions tied to customers.
  - OrderSummary  
    - Joined information of customers and their orders, including SCD Type 2 history.
  - CustomerAggregateSpend  
    - Aggregated daily spend per customer by name.

- Relationships:
  - One Customer has many Orders.
  - Orders are summarized and joined into OrderSummary with historical tracking.
  - OrderSummary aggregates into CustomerAggregateSpend per Name and Date.

- Business Definitions:
  - Customer: An identifiable entity involved in orders.
  - Order: A transaction or purchase with product and quantity details.
  - OrderSummary: A historical, joined dataset from customer and order with SCD Type 2 logic.
  - CustomerAggregateSpend: Sum of daily spending per customer name.


# 2. Logical Data Model

- Customer
  - CustId (Primary Key)
  - Name
  - EmailId
  - Region

- Order
  - OrderId (Primary Key)
  - ItemName
  - PricePerUnit
  - Qty
  - Date
  - CustId (Foreign Key → Customer.CustId)
  - TotalAmount (Computed, PricePerUnit × Qty)

- OrderSummary
  - CustId
  - Name
  - EmailId
  - Region
  - OrderId
  - ItemName
  - PricePerUnit
  - Qty
  - Date
  - [StartDate] (SCD Type 2, optional)
  - [EndDate] (SCD Type 2, optional)
  - [Active] (SCD Type 2, optional)
  - Keys: Composite on CustId + OrderId + Date + SCD fields if present

- CustomerAggregateSpend
  - Name
  - TotalAmount
  - Date

- Relationships:
  - Customer.CustId = Order.CustId (1:N)
  - OrderSummary join on CustId from both Customer and Order
  - CustomerAggregateSpend: many OrderSummary entries → one aggregate per Name, Date

- Normalization:
  - Customer and Order in 3NF (attributes fully dependent on PKs)
  - OrderSummary is a denormalized, historical fact with SCD logic
  - CustomerAggregateSpend is a summary fact, normalized by Name and Date

- Business Rules per Entity:
  - Remove "Null"/Null literals and duplicates in all tables
  - TotalAmount always equals PricePerUnit × Qty
  - Historical SCD Type 2 logic in OrderSummary (maintain full insert/update history)
  - Aggregation on CustomerAggregateSpend: sum of TotalAmount by Name and Date


# 3. Physical Data Model

- Customer (Delta Table)
  - CustId: STRING, NOT NULL, PRIMARY KEY
  - Name: STRING, NOT NULL
  - EmailId: STRING
  - Region: STRING

- Order (Delta Table)
  - OrderId: STRING, NOT NULL, PRIMARY KEY
  - ItemName: STRING
  - PricePerUnit: DECIMAL(18,2)
  - Qty: INT
  - Date: DATE
  - CustId: STRING, NOT NULL, FOREIGN KEY → Customer.CustId
  - TotalAmount: DECIMAL(18,2), computed as PricePerUnit × Qty, NOT NULL

- OrderSummary (Delta Table)
  - CustId: STRING
  - Name: STRING
  - EmailId: STRING
  - Region: STRING
  - OrderId: STRING
  - ItemName: STRING
  - PricePerUnit: DECIMAL(18,2)
  - Qty: INT
  - Date: DATE
  - StartDate: DATE (if SCD Type 2 implemented)
  - EndDate: DATE (if SCD Type 2 implemented)
  - Active: BOOLEAN (if SCD Type 2 implemented)
  - Composite primary key: CustId, OrderId, Date, StartDate

- CustomerAggregateSpend (Delta Table)
  - Name: STRING
  - TotalAmount: DECIMAL(18,2)
  - Date: DATE

- Indexing Strategy:
  - Clustered index on CustId for Customer/Order/OrderSummary
  - OrderId index on Order/OrderSummary
  - Partition by Date for Order, OrderSummary, CustomerAggregateSpend

- Partitioning, Clustering, and Storage:
  - Tables partitioned by Date where appropriate
  - Stored as Delta tables for ACID compliance and SCD support
  - OrderSummary and CustomerAggregateSpend partitioned by Date for query performance

- Constraints:
  - Primary/foreign key relationships as above
  - NOT NULL on key fields
  - Uniqueness enforced on primary key columns
  - Check constraints for TotalAmount ≥ 0

- Performance Optimization:
  - Automatic optimization using Delta file compaction
  - Z-Ordering on OrderId, Date for OrderSummary


# Naming Conventions

- Table names: lowercase, singular (customer, order, ordersummary, customeraggregatespend)
- Field names: CamelCase as in source requirements
- Computed fields: Suffix “Amount,” “Flag,” or “Date” per best practice
